# ProjectOS — Visual Design Spine

> `DESIGN.md` and `EXPERIENCE.md` govern over every supporting mockup, wireframe, import, and exploratory artifact when they conflict.

## Brand & Style

ProjectOS should feel like a carefully maintained project record, not a productivity dashboard and not a chat wrapper. Its posture is **quiet capability**: native, minimal, clean, trustworthy, and specific about what is local, accepted, proposed, uncertain, offline, or about to leave the Mac. Information density is earned by the work; chrome stays restrained.

The selected composition combines the split project masthead from Reference Focused with the context-and-provenance body from Reference Relational. The persistent re-entry surface sits beside the project cover at equal height. Accepted history and relationships sit below. The approved macOS sidebar replaces horizontal artifact tabs. See the [selected Overview direction](.working/design-direction-selected.html) and [approved sidebar direction](.working/sidebar-direction.html); later memlog decisions replace the obsolete cover drawing and the earlier sidebar shown inside the Overview mock.

Motion is part of the craft, but never ornament. A transition must clarify location, causality, state change, or truthful progress. No bounce, shake, confetti, parallax, looping decoration, or automatic Project Map travel.

## Colors

The theme model has two independent axes:

1. **Appearance mode:** Follow macOS by default, or explicit Light/Dark globally.
2. **Theme preset:** Studio Paper by default, with Signal Slate, Quiet Grove, Fjord Air, and Aubergine Ledger also available.

All five exact light/dark palettes are captured above and visualized in the [theme comparison](.working/color-themes-1.html). A global preset supplies the full application palette. A project override may replace only its identity tokens—accent, accent text, selection emphasis, tint, and the two cover marks. It never changes typography, spacing, radii, component behavior, warning/destructive meaning, or accessibility behavior. Reset to global removes the override; later global changes do not overwrite an explicit project preset.

| Preset | Register | Identity use |
|---|---|---|
| Studio Paper | Editorial, warm, grounded; default | Warm brown accent and paper tint |
| Signal Slate | Precise, sober, technical | Deep blue accent and cool slate cover |
| Quiet Grove | Grounded, calm, organic | Forest accent and restrained green cover |
| Fjord Air | Open, lucid, clear | Teal accent and airy blue-green cover |
| Aubergine Ledger | Composed, reflective, distinctive | Aubergine accent and muted violet cover |

System-owned destructive/error colors remain native macOS semantic colors and cannot be themed. Success and warning tokens are fixed parts of each coordinated preset, but state must also be named in text and shape/icon treatment. The visual implementation must verify these load-bearing pairs in every preset and both modes: primary text on canvas/surface/sidebar; muted text on canvas/surface/tint/selection; accent text on accent; accent text or iconography on selection/tint; success and warning when used as text; visible focus indication against adjacent surfaces. Normal text targets at least 4.5:1, large text and essential graphical boundaries at least 3:1, and focus indication at least 3:1 against adjacent colors. Accessibility overrides win over the selected theme.

## Typography

ProjectOS inherits native macOS typography and the San Francisco system family; the implementation toolkit remains deliberately unspecified. Use `{typography.title}` sparingly for project identity and empty-state orientation, `{typography.heading}` for surface and inspector headings, `{typography.body}` for explanations and accepted content, `{typography.label}` for controls and structured metadata, and `{typography.caption}` for provenance and secondary state.

`{typography.code}` is reserved for keyboard shortcuts, manifest/checksum values, identifiers, and literal technical excerpts. Do not use monospaced text as decoration. Type must reflow for Dutch expansion and platform accessibility sizes without truncating essential labels, actions, statuses, or provider disclosures.

## Layout & Spacing

The base rhythm is 4 / 8 / 12 / 16 / 24 / 32 via `{spacing.1}`–`{spacing.6}`. Related content stays tight; major surfaces and semantic shifts receive the larger gaps. Layout favors clear reading order and stable positions over maximizing visible records.

The native project window has a persistent, resizable sidebar and one main content region. Sidebar defaults are documented as tested reference widths—`{spacing.sidebar-default-en}` and `{spacing.sidebar-default-nl}`—not fixed minimums; the user may resize it and the width persists per window. Collapsed width is `{spacing.sidebar-collapsed}`. The project content must remain usable in a reasonably narrow macOS window by stacking secondary rails below primary content, without introducing a separate mobile layout.

On Overview, the Pile Cover and What's Up Next Card form a split masthead and share `{spacing.overview-masthead-height}`. The action card keeps its outer dimensions while Needs recap, Current, and Offline contents replace in place. The relational briefing below holds project description, recent accepted history, accepted relationships, affected work, compact related state, and provenance. The primary content never repeats the masthead's main continuation action.

Conversation uses three regions when width permits: Conversation List, Transcript with Composer, and Proposal Rail. At narrower window widths, the list or rail may collapse into a selectable pane or inspector, but transcript context, proposal status, and explicit approval must remain simultaneously recoverable. Project Map reserves canvas/outline space plus an Inspector; layout stability is more important than graph packing efficiency.

## Elevation & Depth

Hierarchy comes from layout, typography, tonal layering, and hairline separation. Canvas, sidebar, surface, and raised surface tokens carry most depth. Shadows are low-opacity and short, reserved for floating inspectors, menus, the command palette, and cards that must read as objects. Hover must not be the only cue and should never produce large lifts.

Proposal, artifact, Source, and Project Map layers use separation rather than dramatic depth. Pending Change Proposals must never look embedded in accepted Canonical State. A Proposal Inspector may appear above the rail while leaving its originating Conversation visible; the elevation communicates focus, not authority.

## Shapes

Corners are gently rounded and tool-like: `{rounded.sm}` for compact controls, `{rounded.md}` for buttons and rows, `{rounded.lg}` for cards and covers, and `{rounded.window}` for windows, sheets, palettes, and prominent inspectors. `{rounded.full}` is reserved for Status Badges and compact counts. Avoid oversized pills and ornamental blobs.

The Pile Cover is the deliberate exception to ordinary component geometry: the canvas is softly rounded, but every internal mark is data-bound vector geometry. Decorative marks are forbidden.

## Components

The names in this section are the shared component contract and match `EXPERIENCE.md` exactly.

| Component | Visual contract |
|---|---|
| Button | One reusable component with primary, secondary, ghost, destructive, and disabled variants. Intrinsic height; never stretch to fill a card. Primary accent is scarce and reserved for the single most consequential available action. |
| Status Badge | Compact text label plus shape or icon. Pending, accepted, blocked, superseded, offline, and current must remain distinguishable without color. Counts appear only for actionable state. |
| Project Sidebar | Neutral surface, grouped hierarchy, clear active fill plus leading marker plus weight. Project color appears only in active treatment and the project marker. Collapsed labels survive as tooltips and accessibility names. |
| Project Switcher | Project title plus small theme/pile marker and disclosure. It must read as a control, not a profile card. |
| Project Card | Pile Cover above or beside the project title only. No status, last activity, artifact counts, or dashboard metadata in MVP. The entire card is one target. |
| Pile Cover | Deterministic on-device vector drawing using theme tint and cover tokens. Governing Decision blocks, subdued Superseded Decision blocks, unresolved Question outlines, actionable proposal-set marks, and a ground line only. Uniformly scales on overflow; never clips. |
| What's Up Next Card | Same height as the Pile Cover. Title and adjacent Status Badge at top, concise recommendation/context, then intrinsic Button actions and adapter-neutral provider status. No separate return-point header or duplicated historical summary. |
| Relational Briefing | Low-containment sequence connecting project description, recent accepted history, accepted relationships, affected work, related state, and provenance. Lines and numbered markers show sequence without implying a process tracker. |
| Conversation List | Lightweight recency list with selected row, local editable title, Topic filter, search, and actionable proposal state. |
| Transcript | Readable conversational stream. User, agent, incomplete, error, and proposal-generating turns are perceivably distinct; exact source-turn emphasis is brief and non-flashing. |
| Composer | Calm multiline input with grounding and provider status nearby. Draft and disabled-offline states remain legible. |
| Context Preview | Bounded preflight panel naming adapter/provider, local-versus-external execution, scope, selected artifacts/Sources/excerpts, working language, and allowance or cost information when supported. Adapter-specific details fit the shared panel without changing its hierarchy. |
| Proposal Rail | Persistent review region visually separate from Transcript and Canonical State. Supports active-Conversation and project-wide pending scopes. |
| Change Proposal Card | Artifact type, operation, concise summary, source Conversation, proposal set/dependency, and status. Pending treatment can use tint/border but never mimic an accepted Artifact Row. |
| Proposal Inspector | Shared anatomy across artifact types: proposed value, original when edited, effects, dependencies, provenance, diff, status, and explicit actions. Type-specific fields appear only where semantics require. |
| Artifact Row | Current-state-first list row with type, title, meaningful state, and essential relationship/context. No PM-style metadata density. |
| Artifact Inspector | Shared accepted-artifact frame with type, title, status, current content, rationale/context, relationships, provenance, history, and type-aware actions. |
| Relationship Inspector | Parallel inspector for relationship meaning, rationale, provenance, state, affected artifacts, and local/provider actions. |
| Project Map | Quiet canvas plus equivalent structured outline. Nodes and relationships use labels, shapes, line styles, and state text in addition to color. Accepted current state dominates; proposal/history layers are subordinate. |
| Source Inspector | Original and extracted representations, import metadata, language, usage history, referring artifacts/Conversations, and missing/partial evidence states. |
| Notification Center | Durable in-app list grouped/deduplicated by evolving work item. Actionable unread treatment is stronger than informational completion. |
| Progress Indicator | Truthful phase label and determinate progress only when measurable; otherwise restrained indeterminate activity. Never fabricate percentages. |
| Empty State | One plain-language explanation and one primary action, optionally one secondary action. No illustration required and no engagement copy. |
| Settings Row | Native label/value/control pattern with inherited value disclosure for project overrides. Destructive rows are separated at the bottom. |
| Confirmation Sheet | Concise effect summary, affected records/data, explicit destructive or canonical action, safe cancel, and export option when deleting a project. |
| Command Palette | Native-feeling global search/command surface. Active result uses selection tokens plus focus styling; destructive or canonical mutations never execute without their normal confirmation/review. |
| Search Field | Shared current-surface or global search field with scope named in placeholder/label; standard macOS find behavior and keyboard focus. |

## Do's and Don'ts

| Do | Don't |
|---|---|
| Make accepted, proposed, historical, incomplete, and offline state visually explicit. | Use accent color alone to communicate state or authority. |
| Keep current state primary and reveal rationale, provenance, and history on demand. | Turn Overview into an artifact dashboard or PM board. |
| Use one shared component with variants across the app. | Create bespoke buttons, badges, inspectors, or empty states for each artifact type. |
| Keep provider identity and external transmission scope visible before send. | Make browsing, selecting, or opening a project look like it contacted AI. |
| Let project themes provide constrained identity. | Let a project override typography, spacing, component behavior, warning/destructive meaning, or accessibility. |
| Use purposeful continuity motion within `{motion.quick}`–`{motion.deliberate}`. | Animate decoration, bounce, shake, confetti, parallax, or move focus unexpectedly. |
| Keep the Pile Cover deterministic, countable, local, and non-interactive internally. | Add subject imagery, decorative marks, randomness, AI image generation, clipping, or per-mark navigation. |
| Preserve Dutch labels through reflow and adequate width. | Truncate essential actions, status, provider, or accessibility copy to keep a fixed layout. |
| Use native macOS semantic destructive/focus behavior. | Theme error semantics or invent a custom platform interaction model. |
| Keep status/count badges for work requiring attention. | Badge every artifact count or use notifications to manufacture engagement. |

### Open visual decisions

- The precise mapping from native macOS semantic colors to destructive/error and focus-ring rendering is implementation-system-owned and must be verified in the selected UI toolkit; it is intentionally not hard-coded here.
- The Project Map time-comparison visualization and the threshold for promoting a compact Map preview on Overview remain unresolved.
- The working key-screen HTML still uses an obsolete continuity-line cover. Final key-screen mocks must replace it with the governing Pile Cover before promotion.
