# ProjectOS — Visual Design Spine

> `DESIGN.md` and `EXPERIENCE.md` govern over every supporting mockup, wireframe, import, and exploratory artifact when they conflict.

## Brand & Style

ProjectOS should feel like a carefully maintained project record, not a productivity dashboard and not a chat wrapper. Its posture is **quiet capability**: native, minimal, clean, trustworthy, and specific about what is local, accepted, proposed, uncertain, offline, or about to leave the Mac. Information density is earned by the work; chrome stays restrained.

The selected composition combines the split project masthead from Reference Focused with the context-and-provenance body from Reference Relational. The persistent re-entry surface sits beside the project cover; accepted history and relationships sit below. The approved macOS sidebar replaces horizontal artifact tabs. The [Overview mockup](mockups/overview.html) establishes the canonical composition reference; its spine comments identify the governing sections, and this spine remains authoritative over illustrative details.

Motion is purposeful and deterministic. **Quick is 140 ms**, **standard is 220 ms**, and **deliberate is 300 ms**. A transition must clarify location, causality, state change, or truthful progress. No bounce, shake, confetti, parallax, looping decoration, automatic Project Map travel, or animated token streaming.

## Colors

Appearance and theme are independent. Appearance follows macOS on first use, with explicit global Light or Dark alternatives. Studio Paper is the global default theme; Signal Slate, Quiet Grove, Fjord Air, and Aubergine Ledger remain first-class presets in Light and Dark.

The frontmatter uses a strict flat-color contract. The unprefixed roles are the Studio Paper Light default/fallback. At runtime a component resolves every `*-role` value through the selected preset and appearance: `<preset>-<role>` for Light and `<preset>-<role>-dark` for Dark. When Increase Contrast is active, load-bearing roles resolve to `<preset>-<role>-contrast` or `<preset>-<role>-dark-contrast`. Components never read a preset-specific color directly. Project overrides can choose a preset but cannot remap roles.

| Semantic role | Required use |
|---|---|
| `canvas`, `sidebar`, `surface`, `surface-raised`, `text`, `muted` | Structural surfaces and readable content. |
| `decorative-divider` | Optional hairlines only. It may be below 3:1 and must never be the sole cue identifying a control, selection, record, or state. |
| `essential-boundary` | Control/container boundaries needed to perceive an interactive component. |
| `selected-boundary`, `focus-indicator` | Selection and keyboard/accessibility focus; must remain distinct against every adjacent surface. |
| `graph-edge`, `graph-node-boundary` | Meaningful Project Map relationships and artifact boundaries. |
| `pile-decision`, `pile-decision-superseded`, `pile-question`, `pile-proposal`, `pile-ground` | Countable Pile Cover marks. Geometry and line style also identify type/state. |
| `accent`, `accent-text`, `selection`, `tint` | Constrained project identity and emphasis. |
| `success`, `warning` | Named feedback states; never the only state cue. Destructive/error stays native macOS semantic color. |

The committed normal-role contrast minima against their actual adjacent surface, selection, canvas, or tint are: Studio Paper 4.67:1 Light / 6.76:1 Dark; Signal Slate 5.81:1 / 5.28:1; Quiet Grove 5.66:1 / 5.70:1; Fjord Air 5.35:1 / 5.95:1; Aubergine Ledger 5.63:1 / 6.02:1. Increase Contrast load-bearing roles have a minimum of 8.32:1 across the same matrix. Normal text targets 4.5:1, qualifying large text 3:1, and essential graphics, boundaries, selection, and focus 3:1. Accessibility preference handling overrides theme identity.

Project theme overrides replace identity roles only: accent, accent text, selection, tint, and Pile Cover/Map identity roles. They never change typography, spacing, radii, component behavior, warning/destructive meaning, or accessibility behavior. Reset to global removes the override; later global changes do not overwrite an explicit project preset.

## Typography

ProjectOS inherits native macOS typography and San Francisco. Use `{typography.title}` sparingly for project identity and empty-state orientation, `{typography.heading}` for surface and inspector headings, `{typography.body}` for explanations and accepted content, `{typography.label}` for controls and structured metadata, and `{typography.caption}` for provenance and secondary state.

`{typography.code}` is reserved for keyboard shortcuts, manifest/checksum values, identifiers, and literal technical excerpts. Do not use monospaced text as decoration. Type reflows for Dutch expansion and all supported macOS enlargement settings; essential labels, actions, statuses, provider disclosures, and canonical effects never truncate.

## Layout & Spacing

The base rhythm is 4 / 8 / 12 / 16 / 24 / 32 via `{spacing.1}`–`{spacing.6}`. Related content stays tight; major surfaces and semantic shifts receive larger gaps. Layout favors a clear reading order and stable positions over maximum visible density.

The project window has a persistent, resizable sidebar and one main region. `{spacing.sidebar-default-en}` and `{spacing.sidebar-default-nl}` are tested starting widths, not fixed minimums. Width persists per window; `{spacing.sidebar-collapsed}` is the icon-only state. The shell has no account/avatar row, permanent Add Project action, horizontal artifact tabs, or standalone ProjectOS brand mark.

On Overview, Pile Cover and What's Up Next Card share one content-driven grid row at comfortable width. `{spacing.overview-masthead-min-height}` is a reference minimum, never a fixed or maximum height. The cover stretches to the action card's intrinsic height. When available width, Dutch expansion, or system text enlargement would clip essential content, the cards stack and grow independently. The read-only project description and relational briefing follow below; editing the description belongs in Project Settings.

Conversation uses Conversation List, Transcript/Composer, and Proposal Rail when width permits. Narrow layouts transform list or rail into a recoverable pane without hiding current proposal status or approval effects. Project Map provides canvas or synchronized outline plus Inspector; the outline and inspectors reflow normally even though the canvas remains two-dimensional.

Motion implementation uses the three constants above: 140 ms for local control feedback, 220 ms for navigation/pane continuity, and 300 ms only for deliberate state transitions such as an atomic accepted-set reveal. Sidebar pointer resize and direct manipulation are immediate. Reduce Motion replaces spatial movement, scaling, and animated scrolling with immediate state replacement or, when continuity still helps, a short opacity-only 140 ms transition.

## Elevation & Depth

Hierarchy comes from layout, typography, tonal layering, and intentional boundaries. Canvas, sidebar, surface, and raised-surface roles carry most depth. Shadows are low-opacity and short, reserved for menus, command palette, floating inspectors, and cards that must read as discrete objects. Hover must not be the only cue and never produces a large lift.

Pending proposals must never look embedded in accepted Canonical State. Proposal and historical layers use separation, border/line style, and labels rather than dramatic elevation. Elevation communicates current inspection, never authority.

## Shapes

Corners are gently rounded and tool-like: `{rounded.sm}` for compact controls, `{rounded.md}` for buttons and rows, `{rounded.lg}` for cards and covers, `{rounded.window}` for sheets/palettes/prominent inspectors, and `{rounded.full}` only for Status Badges and compact counts. Avoid oversized pills and ornamental blobs.

Pile Cover is the deliberate exception: its softly rounded canvas contains only countable vector marks. Governing Decisions are solid rectangles; Superseded Decisions remain in place with an outline/hatch treatment; unresolved Questions are outlined, ground-level, and deterministically tilted; actionable proposal sets are dashed floating squares; the ground is a line. Fill, hatch, outline, dash, tilt, label/legend, and position—not color alone—carry meaning. Decorative marks are forbidden.

Project Map similarly uses node shape, labels, edge direction, line style, and state text alongside color. Current, Needs review, Historical, and Proposed relationships must remain identifiable in grayscale and with Differentiate Without Color enabled.

### Pile Cover geometry and stability

1. Process Governing Decisions in immutable first-appearance order. Place each solid, consistent-size rectangle bottom-up in the first course with room; if none has room, start a new course.
2. Mark size never encodes duration, importance, effort, actor, or agent provenance. Directly authored and accepted-agent Decisions have equal visual authority.
3. Once placed, a Decision block never changes order or relative position. New Decisions append around the established composition. Supersession changes styling in place and adds the replacement as a new block.
4. Unresolved Questions sit at ground level to the right in immutable first-appearance order, using a restrained repeating alternating tilt. Their appearance/disappearance never repacks Decision blocks.
5. One dashed fixed-size mark per actionable proposal set floats centered above the pile. A set is actionable when it contains Pending or Needs review members; Deferred, Blocked, Rejected, Accepted, and Accepted with edits are excluded. Partial acceptance retains one mark until no actionable member remains.
6. Bare ground plus unresolved Questions is the valid new-project state. One responsive renderer serves Project Library cards and Overview hero only.
7. The renderer supports at least 40 Decision blocks. Overflow uniformly scales the complete composition while preserving relative geometry; it never clips, scrolls, hides, or reorders marks.
8. Theme and appearance changes recolor without re-layout. Rendering is on-device, offline, deterministic, and makes no network/provider request.
9. Export stores canonical records, cover-relevant state, and theme; restore regenerates the same cover. No rendered asset is required. Sidebar, share, and print do not render a pile in MVP.

## Do's and Don'ts

| Do | Don't |
|---|---|
| Make accepted, proposed, historical, incomplete, offline, and disabled-with-reason state explicit. | Use color, position, animation, or a transient toast as the sole state cue. |
| Resolve every component color through the active semantic theme role. | Bind component styles directly to Studio Paper or another preset namespace. |
| Use `decorative-divider` only where removing it loses no component/state meaning. | Use a low-contrast hairline as an essential control, selection, graph, or pile boundary. |
| Keep current state primary and reveal rationale, provenance, and history on demand. | Turn Overview into an artifact dashboard or PM board. |
| Use the same shared components and variants across the app. | Create bespoke buttons, badges, inspectors, or empty states for artifact types. |
| Keep provider identity and external transmission scope visible before send. | Make browsing, selecting, importing, or opening a project look like it contacted OpenAI. |
| Let project themes provide constrained identity. | Let projects override typography, spacing, behavior, error meaning, or accessibility. |
| Use 140/220/300 ms only for purposeful continuity and truthful state change. | Use timing ranges, decorative movement, bounce, shake, confetti, parallax, or unexpected focus travel. |
| Keep Pile Cover deterministic, countable, local, stable, and internally non-interactive. | Add duration sizing, subject imagery, actor weighting, decoration, randomness, AI images, clipping, or per-mark navigation. |
| Let Overview masthead grow and stack when content requires. | Clip Dutch/large-text copy to preserve a 120 px fixed height. |
| Preserve Project Map meaning through canvas and synchronized outline. | Make spatial position or color the only way to understand a relationship. |
| Use native macOS destructive semantics and system accessibility preferences. | Theme destructive meaning or override Increase Contrast, Differentiate Without Color, Reduce Transparency, or Reduce Motion. |

### Deferred after MVP

- Ollama and other provider adapters, including their installation, model-management, privacy, offline-inference, and error UX.
- Animated or explicit Project Map time-comparison views and a compact graph preview on Overview.
- Source importers for DOCX, RTF, HTML, images, archives, and structured chat exports; OCR remains outside MVP.
- Pile Cover rendering for share and print.
